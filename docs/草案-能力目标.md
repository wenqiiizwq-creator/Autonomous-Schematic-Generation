## 1. SKILL.md「能力目标」逐字改动（纲要）

原文（整节）：
```
ASG 的输入是一块板卡的设计需求，输出是设计方案确定后的电路原理图。ASG 的能力体现在三项，架构、核心原则和主流程都为它们服务：

1. **选对功能电路**：为每项设计需求和系统规格选择合适的功能电路。整板层由 C2 定跨块的决定，功能电路层由 C3 在块规格内选方案和核心器件。
2. **设计合理，不过度设计**：电路在全部工况下满足需求和器件的保证条件；以满足需求为限，不欠设计，也不过度设计。C3 定方向，C4 落实到外围、计算和器件，C5 闭合跨块配合。
3. **图面清晰易读**：模块清晰，图形连接明确，方便人阅读。由 C6 按 P4 和绘图纲要 O1–O8 画出并审阅。

评测 ASG 按能力模块分别进行：每个模块用标准上游作给定输入单独评测；从需求串联到交付的整板运行作集成测试。
```

改为：
```
ASG 的输入是一块板卡的设计需求，输出是设计方案确定后的电路原理图。ASG 的能力是把电路设计得合理，把图画清楚，并能发现自己知识不够的地方加以改进。架构、核心原则和主流程都为这些能力服务。

**合理**指同时做到下面五条，不以经济成本为准：

- **充分**：稳态、瞬态、上下电、故障和极限环境下，都满足需求和器件的保证条件。
- **必要**：每个器件、每一级、每档裕量都有来由。去掉它或取小一档后其余四条仍然成立的，就是过度设计。
- **匹配**：方案适合它的工况，不用在适用范围的边缘；器件之间、块之间相互适配。
- **稳健**：对容差、温度、老化和单一故障有确定的表现；保护两侧都成立，不误动，也真能保护。
- **有据**：每个决定的依据是需求、手册保证值或计算，不是印象或典型值。

能力分七项：

1. **把设计问题定准**（C1）：需求里的工况是完整的，输入范围、负载、环境、接口对端和故障情形都有数或已澄清。能看出哪个缺失的条件会改变方案或取值，并把它问清。
2. **整板结构合理**（C2）：每条需求落到确定的功能块；电源树的级数和各级电压有来由；隔离和电压域的边界放在需求要求的位置；块与块之间用少数几个参数就能说清；一个块的故障不会无保护地传到别的块。
3. **功能电路选得合适**（C3）：选定方案的适用范围覆盖本板工况；都能满足的候选里选结构最简单、依赖最少的，选更复杂的要有需求、标准或手册上的理由；核心器件靠保证值覆盖决定条件。
4. **电路实现正确且有度**（C4）：外围电路按手册的应用条件接全，每个引脚有着落；取值按最坏情况算出，应力在降额之内；裕量够用，不无故取高；环路、启动和关断成立。
5. **异常工况与全板配合成立**（C4 管块内，C5 管跨块）：过压、过流、反接、短路、掉电和热插拔下电路的表现是确定的；保护门槛两侧都成立，上下级保护有先后；跨块的电平、时序、电源预算、复位和故障传递相互适配；对外端口的防护与它面对的环境相称。
6. **图面清晰易读**（C6）：模块清晰，图形连接明确，读图的人能沿功能路径看懂电路。按 P4 和绘图纲要 O1–O8 画出并审阅。
7. **知道自己哪里知识不够，并据此改进**：设计中遇到库里没有、依据不足或回到上游重做的地方，如实留下记号，不用印象补上。每次运行由工具从各模块的产品里抽出知识缺口清单；跨多次运行和评测，把重复出现的缺口归纳成能力缺陷，改进后用题目验证。

评测 ASG 按能力模块分别进行：每个模块用标准上游作给定输入单独评测；从需求串联到交付的整板运行作集成测试。判定按合理性五条：充分不成立的算不通过，稳健不足的算风险，必要不成立的算过度设计、单独计数。
能力缺陷的归纳和改进在评测侧做，不在单次设计里做。每条缺陷带一道能稳定暴露它的题目；改进之后这道题通过、留出的题目没有变差，才算修好。
```

## 3. 跟着改的实现

- 新脚本 `scripts/knowledge_gaps.py`，从已有记录抽信号，每条写模块、任务、信号类型、对象（块、角色、位号或计算编号）和出处：

  | 信号 | 从哪里抽 |
  |---|---|
  | 典型电路库没有适用方案 | `block-circuits/` 里选定方案没有标典型电路的块 |
  | 候选来源未证实 | `scheme-criteria.json` 的 `unverified` 候选 |
  | 手册不在知识库 | 打包列出的 `datasheets_to_file` |
  | 依据是典型值、估计或未规定 | `design-closure.json` 计算参数与门槛的依据 |
  | 外部资料待办 | `design-closure.json` 的 `external` 待办 |
  | 回到上游重做 | `modules.json` 的 `returns` |
  | 用户否定了建议 | `requirements.json` 澄清答复与建议条文不同的；`selection.json` 确认记录里选的不是推荐候选的 |

- `deliver.py` 在生成报告前调用它；`pack_design.py` 要求清单存在且与当前记录一致。
- 设计报告加一小节“知识缺口”，按信号类型给出数量和清单。
- `references/delivery-report.md` 写清单格式；`references/modules.md` 的 `returns` 一节指向它。
- 测试：每种信号一例；清单与记录不一致时打包报错。

不做的：
- 不恢复 `lessons.json`、经验总结任务和改进台账。清单是抽出来的，不是写出来的。
- 同一关卡反复不过的次数，现在没有记录来源，本步不抽。要统计就得让 `check_module.py` 记每次运行的结果，另议。
