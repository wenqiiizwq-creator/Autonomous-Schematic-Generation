本草案涉及纲要的以下部分，按「纲要的修改」须你确认后才写入：能力目标、架构、P 原则、主流程任务与做完的标志、选择工作流。第 10 节是需要你定的事。

## 1. 为什么改

现在 ASG 只能从需求一路做到交付，评测也只能看最终的整板。这有四个问题：

1. **分不清错在哪一层**。整板上的一个缺陷，可能来自需求读错、方案选错、计算漏项，也可能只是画图出错，最后都记在交付物上。比如 Matrix 板的方案题从 14 道 found 掉到 7 道，没法拆出多少是能力退步、多少是评判说明变了。
2. **上游错误会一路传下去**。架构错了，下游再好也拿不到分，下游的能力因此测不准。
3. **样本太少**。一次整板运行只得到 3 个样本，评测集的 52 个案例只能在整板里间接用到。
4. **改进效果对不上**。改一条计算规则，要重跑整板才能看到效果，结果里还混着其他步骤的随机差异。

## 2. 划分依据（第 2 稿新增）

“能力”可以有两种切法。

- **按技能切**：读手册、最坏情况计算、方案比较、找料、画图。
  这种切法最“纯”，但这些技能散布在多个步骤里，没有自己的输入和产出文件，不能拿固定输入单独运行，也给不出标准答案。
- **按交接点切**：在设计流程中天然有成品的地方切开，比如确认后的需求、板级方案、块电路、网表。
  这样每个模块都能拿固定输入单独运行，产出也是工程师认得的东西，可以和工程师版对照。

草案按交接点切模块。技能维度不做模块，而是作为评测标签横跨各模块统计，比如“手册引用对错”在 C3–C5 都统计。

每条边界要满足三个条件，第 1 稿有几条边界不满足，第 2 稿改了：

| 条件 | 含义 |
|---|---|
| 有成品 | 交接物是工程师认得、能单独评判的东西 |
| 不泄题 | 给下游的标准输入不能把下游要做的决定写进去 |
| 回流少 | 下游常常要回头改上游的，就不该切开 |

## 3. 模块划分

| 模块 | 能力 | 给定输入 → 产出 | 对应任务 | 服务的能力目标 |
|---|---|---|---|---|
| C1 需求理解与澄清 | 读懂需求，找出影响设计的缺口并问对问题；定降额等级；建立追溯 | 需求文件 → 确认的需求清单 | 1.1 | 前提 |
| C2 板级方案 | 定功能块、电压域、电源树、隔离边界的位置、跨块流向和对外接口 | 确认的需求 → 板级方案 `architecture.json`，含每块的块规格 | 1.2 | 选对功能电路（整板层） |
| C3 块电路选择 | 按块规格选功能电路方案和核心器件，并与其他候选比较 | 块规格 → `scheme-criteria.json`、核心角色的 `selection.json` | 1.3、1.4 | 选对功能电路（功能电路层） |
| C4 详细设计与器件选型 | 按手册定外围电路，按工况算应力、定器件性能要求，选出满足要求的器件，再用实际器件参数复核 | 块电路 → `reference-input.json`、计算、`component-requirements.json` | 2.1、2.2、2.3 | 设计合理、不过度 |
| C5 全板闭合 | 写出设计网表；检查跨块电平、电源域与时序、引脚处置；做 FMEA 和 EMC 端口矩阵 | 各块设计 → `electrical-intent.json`、闭合矩阵 | 2.4，及 5.1 中的设计闭合部分 | 设计合理 |
| C6 原理图绘制 | 只凭网表定分组与分页，画成可读的 KiCad 工程，并通过图面检查 | 网表 → KiCad 工程、`summary.json`、`visual-review.json` | ③、④ | 图面清晰易读 |
| 交付（编排，不是模块） | 汇总各模块状态，出报告并打包 | — | 5.1 汇总、5.2 | — |

### 与第 1 稿的差别和理由

1. **C2 与 C3 的边界重切，按“整板层 / 功能电路层”分。**
   - 第 1 稿把“系统架构”交给 C2，但 1.3 又把“隔离方式”列为关键块方案，两边都在定隔离。给 C3 的标准架构里如果写了“反激隔离 5 V”，C3 的题就被泄掉了。
   - 第 2 稿的分法：
     - C2 定**跨块的决定**：隔离边界在哪、电源树怎么分、各块的块规格（输入、输出、功率、指标），只写“要什么”；
     - C3 在块规格内决定**怎么实现**：反激还是正激、集成 PD 还是分立、光耦还是数字隔离器。
   - 这也就是你前面说的“功能电路层 / 整板方案层”两层。
2. **第 1 稿的 C4、C5 合并为新的 C4 详细设计与器件选型。**
   - 两者回流太多：计算要用实际器件的参数（TVS 钳位电压、MOSFET 导通电阻、栅电荷），选了器件又要回头复核计算。
   - 工程师版只有最终器件，没有“性能要求”这个中间物，单独评选型就没有标准输入可用。
   - 器件真实可采购（A3）和过度设计（A1）仍在 C4 内单独统计。
3. **C6 绘图（第 1 稿 C7）只读网表。**
   - 第 1 稿让它同时读架构和功能块划分。但分组、分页本身就是可读性能力的一部分，给定了就测不到这部分能力，用工程师网表评测时也没有这些文件。
   - 串联运行时，C2 的板级方案可以作参考。单独评测时不给。
4. **自检、改版、串联仍不单设模块**。理由同第 1 稿：
   - 自检就是每个模块的关卡，是否如实由“埋设有问题的给定输入”题和集成测试的 A5 来测；
   - 改版是编排路径，它独有的“改动受控”在编排层检查；
   - 串联就是集成测试。

### 仍然坚持的部分和理由

- **按交接点切而不按技能切**：理由见第 2 节。按技能切的模块不能单独运行，也就不满足“独立能力模块”的本意。
- **核心器件随 C3 走**：很多功能电路就是由核心 IC 定义的（如 PoE 的 TPS23753A 集成方案），评测集的方案题也连着核心器件一起判。拆开会让 C3 交出一个没有器件的方案。
- **C1 单独成模块**：问对问题是独立的能力，用埋设缺口的需求就能单独测。需求清单是天然的成品，回流也少：中途发现的缺口按现有规则补问。
- **C5 单独成模块**：跨块问题（电平不匹配、上电时序、引脚处置）在块内设计时看不到，是独立的能力。它的代价是要新建埋设跨块缺陷的题，所以放在评测的最后一批。

## 4. 模块契约

各模块的统一规则如下。

- **给定输入只读**。单独运行时，上游文件由任务书给出，带 SHA-256，模块不得修改。
- **发现给定输入有问题时**（方案在某工况下不可行、需求自相矛盾）：
  - 单独运行：登记新类型的待办 `INPUT`，写明证据和建议，不能自己改上游；
  - 串联运行：回到上游模块重做，写明回退原因，下游重新跑。
- **关卡过了才交给下游**。关卡是现有的“做完的标志”按模块重新归组，由 `check_module.py <模块> <设计目录>` 统一调用现有检查。
- **产出写明依据**。每个模块完成时，在 `record/modules.json` 写下读过的上游指纹、产出指纹和关卡结果。上游指纹一变，下游就标为 STALE，沿用 `check_delivery_freshness.py` 的做法。

| 模块 | 产出 | 关卡（沿用现有标志） | 需要补的 |
|---|---|---|---|
| C1 | `design-closure.json` 中的 requirements、clarifications、降额等级、guideline_scope | 1.1 | `audit_design_closure.py --module C1` |
| C2 | **新增 `architecture.json`**：功能块、电压域、电源树、隔离边界、跨块流向、对外接口，以及每块的块规格 | 1.2，改为机读检查 | 现在架构只画在第 1 页、记在 page-plan 的 blocks 里，没有机读产出 |
| C3 | `scheme-criteria.json`、核心角色的 `selection.json` | 1.3、1.4；选型确认暂停点不变 | `check_scheme_criteria.py` 现在会顺带读 page-plan，这项交叉检查移到 C6 |
| C4 | `reference-input.json`；`design-closure.json` 中的 calculations、operating_points、derating、evidence；`component-requirements.json` | 2.1–2.3 | `audit_design_closure.py --module C4` |
| C5 | `electrical-intent.json`；`design-closure.json` 中的 pin_dispositions、net_voltages、matrices；FMEA 和 EMC 端口矩阵 | 2.4，加 5.1 中的矩阵、FMEA、EMC 条目 | 全量审计放在这里 |
| C6 | `page-plan.json`、图页脚本、KiCad 工程、`summary.json`、`visual-review.json` | ③、④ | 支持只给 KiCad XML 网表作输入（复用 Circuit IR 与重画基线逻辑）；OrCAD 网表后做 |

**design-closure.json 不拆文件**。它跨了 C1、C4、C5 三个模块，按区段划分归属：每个区段只由所属模块写，审计加 `--module`。拆文件会让 1600 多行的审计大改，记录也会变多，和你清理记账的方向相反，所以不推荐（见 D3）。

## 5. 运行与编排

**任务书（task.json）**：在 v1 上加一个可选字段。没有这个字段时就是现在的整板流程。

```json
"modules": {"from": "C4", "to": "C4",
            "given": {"design-closure.json": {"path": "...", "sha256": "..."}}}
```

**交付**：单独运行时：
- 交付目录装 record 文件和“模块报告”，由 `render_design_report.py` 只出已跑模块的章节；
- result.json 的必需角色按已跑模块确定。

这会改动与外部流程（pack-result）的接口，见 D5。

**暂停点不变**：C1 的需求澄清、C3 的选型确认仍是固定暂停点；无人当场答复时，只认任务书里的答复和代答授权。

**选择工作流改为编排**：

| 工作 | 编排 |
|---|---|
| 从需求做新设计 | C1 → C6，加交付 |
| 给已有工程新增模块 | C1（只读相关需求）→ C3 → C6；改动已有网络时按改版 |
| 重画已有工程，电气不变 | 只跑 C6，给定锁定的基线网表 |
| Value 参数修改 | C4 局部修改，再走 C6 的补丁路径 |
| 电气改版、处理审查意见 | 从受影响的最上游模块开始，下游按指纹重跑；编排层检查改动受控 |

## 6. 评测挂钩

每个模块评测时，给定输入一律用**标准上游**（工程师版，或经你裁决的版本），保证分数不被上游错误污染。

| 模块 | 评测输入 | 判什么 | 题从哪来 |
|---|---|---|---|
| C1 | 埋了缺口的需求文件 | 该问的问到没有（查全），不该问的有没有乱问（误问），追溯是否完整 | 要新建 |
| C2 | 已确认的需求 | 功能块、电压域、电源树、隔离边界、块规格，与工程师架构对比 | 现有 3 块整板，加新板（Matrix 核心、小型、模拟、高速） |
| C3 | 块规格（不含拓扑） | 方案题 found/partial/missed，另计“未比较”条数 | 现有 scheme.json 挂在整板上，要下放到案例，改写成块规格 |
| C4 | 块规格、标准方案和核心器件 | 测试点、计算对错、外围漏项、A3 真实可采购、A1 过度设计、A2 成本 | 现有案例的测试点大多在这层；overdesign.json |
| C5 | 各块的标准设计 | 跨块缺陷：电平、电源域与时序、引脚处置 | 要新建埋设跨块缺陷的题 |
| C6 | 只给网表（工程师网表或 ASG 网表变体） | 网表逐脚一致、ERC、R1–R5 | 评测集已有工程师和 ASG 网表变体 |
| 集成 | 整板需求 | 现行整板评测标准：G1、G2、M1、M4、A5 | 现有 3 块整板 |

跨模块的技能标签按模块分别计数，不单独出题：手册引用对错、最坏情况计算对错、候选比较是否成立。

评测集 README 要加一节“模块评测”，与现行“整板评测”并列。整板评测可以从每板 3 次降到 1–2 次，由你定。

## 7. 怎样验证这个划分

划分是否合理，用三项检查来验，放在实施第 2 期：

1. **单独与串联可比**：同一块板，模块单独运行（给标准上游）和串联运行（给自己的上游）的产出逐项对照。差异应能归到上游输入的差异上，不能归到的说明边界切错了。
2. **不泄题**：拿 C3 的标准块规格给一个不跑 ASG 的评判看。如果能直接读出方案，就要改块规格的写法。
3. **回流统计**：串联运行时，统计各模块回退到上游的次数。某条边界回退频繁，就考虑把两边合并。

## 9. 风险与取舍

| 风险 | 应对 |
|---|---|
| 记录变多 | 只新增 `architecture.json` 和 `modules.json`，不新增人读文档 |
| 设计变死板 | 串联运行时允许回退到上游，只有单独运行时才禁止修改上游 |
| 各模块都过、整体不通 | C5 负责跨块配合，集成测试兜底，集成测试不能省 |
| 评测准备成本 | C3、C4、C6 能直接用现有材料；C1、C2、C5 要新建题 |
| design-closure.json 仍是大文件 | 靠区段归属和按模块审计控制耦合；以后耦合再出问题再拆 |

> 评测 ASG 按能力模块分别进行：每个模块用标准上游作给定输入单独评测；从需求串联到交付的整板运行作集成测试。
