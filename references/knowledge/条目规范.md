# 条目规范

各组件的条目共同遵守的写法。各组件自己的条目格式（有哪些栏目）写在该组件的 `README.md`，这里只写共同的部分，组件说明不再重复。

## 共同要求

1. **有来源**。每条写出处：原件在框架的 `原件/` 里的路径和页码，或标准号与条款。没有来源的不写。
2. **写条件，不写结论**。写“在什么条件下适用、要满足什么”，不写某块具体板子的取值或结论。
3. **不绑使用方**。条目里不写某个技能、流程或工具的任务编号、文件名、脚本名；设计、审查和以后别的硬件开发流程都要能读。
4. **不重复**。一件事只在一个组件里写，别处引用。例如降额系数只在设计准则的 G10，计算方法里写编号引用它。
5. **可判**。能写成数值条件的写数值条件，便于用工具核对。

## 条目放在哪里

| 要写的内容 | 放在 |
|---|---|
| 必须成立什么（判据、工程取值、降额） | `设计准则/`，按它自己的修订和发布流程改 |
| 需求里要给定哪些条件；行业标准规定的环境与电磁等级 | `需求要素/端口/`、`需求要素/全板/`、`需求要素/环境与电磁等级/` |
| 整板的结构问题有几种做法 | `板级架构模式/` |
| 两个功能块之间要交代哪些量；总线与电平的电气约定 | `接口约定/参数模板/`、`接口约定/总线与电平/` |
| 一个功能有几种实现方案 | `典型电路/<知识域>/` |
| 一类电路的元件值怎么一步步定 | `计算方法/<知识域>/` |
| 某个型号的手册保证值 | `器件参数/<器件分类>/` |
| 一类器件怎么坏；故障分析按什么步骤做 | `失效与故障分析/器件失效方式/`、`失效与故障分析/分析步骤/` |
| 一块审查过的公开工程整板怎么搭、哪里有问题 | `设计实例/<功能分类>/`，审查留下的记录在 `设计实例/审查记录/` |

典型电路和计算方法共用一套知识域：电源变换、入口保护与配电、信号与模拟、总线与接口、数字核心与时钟复位、驱动与执行、隔离与安规。典型电路另有“测试与调试”，计算方法另有“通用方法”“热与寿命”。一个条目跨两个域时，放在它的核心器件所在的域。

## 来源的写法与核对

- 条目开头列来源清单：`- S1：<相对 原件/ 的路径>`。来源是一整个目录（如一套参考设计）时写目录。
- 表格最后一列叫“来源”，写 `S1 p43`，可带表号或条款号；一行引几页写 `S1 p43、p50`。正文里写 `（S1 p50）`。
- 页码用 PDF 文件页序，逐页抽取确认（`pdftotext -f N -l N`）。整本抽取后数换页符，在有横排页的文件里会数错。
- 知识库没有标准原文、用厂家应用笔记转述的，在条目里写明不是引自原文。
- 来自设计审查或设计评审的已知问题，写 `审查发现：<审查名或板名>，<编号>` 或 `设计评审：<日期>，<事项>`；原记录在项目里，尽量再给手册页或标准条款作第二出处。

核对工具（在框架根目录运行）：

```
python3 工具/check_sources.py <条目或目录>
```

它逐行核对：来源文件存在、页码存在、带“来源”列的表格行里的数能在所引页的文字里找到。新条目都要过这项核对。

- “来源、参数、符号、条件、说明、量、谁给、为什么要、步、定什么”这些列不核数；准则编号、指向其他条目的链接不当作数。
- 一行引几份来源时，格子里的数要在每份来源的所引页都找得到，所以带数的行尽量只引一份来源。
- 原件是扫描件或抽不出文字时，工具列为“没核对”，由人对图确认；[原件勘误](原件勘误.md) 列出文字层有问题的原件（例如把“微”抽成“毫”）。

## 原件放在哪里

条目引用的原件都复制在框架的 [`原件/`](原件/README.md) 里，目录和文件名与知识库的 `HardwareWiki/raw/` 相同，所以来源清单里的路径两边通用。核对工具只读 `原件/`，框架不依赖原件库就能核对。

新资料仍先下载到 `HardwareWiki/raw/`（它是全部资料的总库），条目写好来源清单后运行：

```
python3 工具/collect_sources.py          # 把条目引用到而 原件/ 里还没有的复制进来
python3 工具/collect_sources.py --check  # 只列出缺的和没有条目引用的
```

参考设计、评估板这类一套资料，只引其中用到的文件（原理图、设计指南、测试报告），不整套搬进来；它们在 `原件/设计实例/厂家参考设计/`，来源清单写 `设计实例/厂家参考设计/…`。

`原件/设计实例/公开工程/` 是未经审查的公开工程，**不能写进条目的来源清单**，核对工具会报错。它只用来普查实际工程里出现了什么；其中标为“留出”的仓库不要打开，见 [公开工程的说明](原件/设计实例/公开工程/README.md)。条目里也不写某个公开工程的电路或取值。审查过的公开工程写成 `设计实例/` 的卡片，卡片的依据同样是手册页和准则，不是工程本身。

## 与设计准则挂钩

条目落实或支撑哪条准则，就写出准则编号（`G04-017` 这种）。`工具/rule_support.py` 据此生成 [准则支撑表](索引/准则支撑表.md)；条目写了登记里不存在的编号会报错。准则里已有的判据和取值只写编号，不重抄；建条目时发现准则有问题，登记到 [准则反馈](建设记录/准则反馈.md)，不直接改准则。

## 改完条目之后

```
python3 工具/collect_sources.py     # 条目引了新原件时，收进 原件/
python3 工具/check_sources.py <改过的条目>
python3 工具/rule_support.py        # 重新生成 索引/准则支撑表.md
python3 工具/build_index.py         # 重新生成 索引/条目总表.md
```

改完并过了核对之后，按 [版本记录](版本记录.md) 的规则升版本号并加一行。

条目的增减只体现在 [条目总表](索引/条目总表.md)，各组件说明里不再手工维护条目清单。
