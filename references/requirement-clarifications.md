# 需求澄清：当场问用户，答复写进需求基线

需求没说清、而设计要靠它定时，**当场问用户**，用户答复后**马上写进需求基线**，再按定下的需求往下设计；
不把“需求没定”留到交付时才问（2026-10-27，用户：在 ASG 的设计中遇到需求未明的问题时，也应该及时和用户沟通）。
问题和答复写在 `设计资料/需求基线.md` 的澄清条文里：编号 CL-…、问题、采纳的条文、答复人与依据（[quick-design.md](quick-design.md) 第 1 步）。

## 问什么

只问证据和工程判断解决不了、且确实要用户决定的产品取舍：需求没写、写得含糊、前后矛盾或尚未确认。
先查需求文档、接口约定和已确认的对话，问题里写明查过什么。与本设计无关的模板空白不问。

| 情况 | 处理 |
|---|---|
| 需求没写、含糊或冲突，且会改变架构、选型、设计值或保护目标 | 当场问 |
| 需求已定，缺原厂资料 | 写进报告的“未核实与待验证”，不问 |
| 设计约束没给（环境温度、裕量），在合理取值范围内选型和取值都不变 | 写明假设及出处（行业常用、厂家建议），不问 |
| 同上，但取值会改变选型或取值 | 问 |
| 启动计算要用的启动期负载（阻性/恒流/恒功率的值）需求没给，负载又不在本板上（用户 2026-11-04） | 问，附按需求上限算的结果和推荐值；不把估计值写进算式 |
| 降额等级（I/II/III 级）需求没写 | 问，附建议等级（按 降额规范（框架降额与应力目录的 `降额规范.md`）“降额等级从哪来”一节，写明产品失效后果和工作方式）；暂缓的按建议等级作为写明的假设 |
| 可预见的误接或对外暴露（反接、对外接口 ESD、用台架电源代替规定的源）需求没提，后果只是本板可更换的局部损坏 | 写成假设或交给后续环节的约束，不问 |
| 同上，但后果涉及安全（起火、触电、无保护电池被短接），或会让需求内的功能失效 | 问，问题里写明危害路径和推荐的电路方案 |
| 实际热、布局、实测等后续环节的事 | 写成交给后续环节的约束，不问 |
| 成本估算超过需求的目标，或设计改动要在成本、体积、余量之间重新取舍 | 问，附估算和各方案的代价（R8：加了器件却没估成本） |
| 答复只定了一侧界限，另一侧会影响功能（只定了 LED 电流上限，亮度下限决定看不看得清） | 答复时当场确认另一侧，不留到设计中途 |

一个独立决定只问一次，同一个决定影响多处时只建一项；不同参数即使来自同一本需求书，也不合并。

## 建议条文不加严

建议条文在代答授权下会被直接采纳成需求，后面的电路要逐条满足它。所以（H-001 2026-11-16：12 条需求经澄清变成 34 条，
其中“负载理想阶跃时仍在 ±4 % 内”“接反可持续任意时长”“全程 +70 ℃ 满载 5 年”都是建议条文自己加的）：

- **取最宽松的读法**。需求没写的工况，建议条文取与需求原文相容、对设计要求最低的那种读法。原文、对端接口或所引标准没有要求的最坏叠加
  （理想阶跃、任意时长、全程最高温满载）不写进条文。
- **条文不定出只有专门电路才做得到的限值**。需求没给门限、延时、精度或持续时间时，建议条文写功能和方向，数值写成“取所选器件的保证值，记入接口说明”，
  不把需求的容差边界当成动作门限或保证值。例：需求只写“输出电压正常时 PG 为高阻，不正常时拉低”，建议条文写“稳态输出一定落在正常一侧，
  输出未建立或掉电时为不正常；动作门限取所选稳压器件自带的窗口”，不写“低于 3.168 V 或高于 3.432 V 必须拉低”
  （H-001 2026-11-16：后一种写法使 PG 一项多出比较器、基准和监控芯片三颗集成电路和四条计算）。
- **做不到时先放宽自拟的条文**。某条由建议条文采纳成的需求做不到，或要加器件、换方案才做得到时，先看这条条文里超出需求原文的部分，
  把它放宽到现有方案做得到（代答授权下改建议条文并重新采纳，澄清里记下改前改后和原因）；原文本身的要求才改方案。
- **多做的列为可选项**。需求没要求、但设计者认为值得做的保护和裕量，写进设计报告的“可选项”，附代价（多几颗器件、多少成本或面积），
  不写进建议条文。代答授权只采纳建议条文，不采纳可选项；用户当场答复时可以自己选。
- **答哪一种都不改图的不提**。一条澄清只定一个会改变电路、器件或限值的决定。两种答复画出同一张图的写成假设，不建澄清。

## 什么时候问、答复怎么记

- 读完需求后盘点一遍要用户定的问题，**一次汇总问用户**，不逐颗器件打断；设计中途又发现新的需求依赖，停下来问。
- 处理审查意见时，要用户定需求的意见同样当场问。
- 答复只有三种：用户给定条文；采纳 ASG 的建议条文；用户明确暂缓（按建议条文设计，在需求基线里标明是假设，并列入报告的“未核实与待验证”）。
  用户一时定不下来时，只能采纳建议或明确暂缓，不能“先挂着”。
- **给定或采纳后，问用户要不要直接改原始需求文件**（2026-10-27，用户：ASG和SR都需要提示用户，是否直接更改原始的需求文件。用户确认后，直接改）。
  问的时候点名改哪个文件的哪一处，给出要写入的文字；用户确认后马上直接改，不确认就只写进需求基线。
- 无人当场答复时，见 [任务书](workflow-handoff.md) 的 `clarification_answers` 和 `delegation`：答复人写任务书的出题人或代答人，依据写任务书的字段。
