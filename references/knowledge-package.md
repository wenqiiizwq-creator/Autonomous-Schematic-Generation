# 知识框架的用法

`references/part-roles.md` 回答"这类器件干什么"；知识框架回答"这个功能通常怎么实现、需求要给什么、块之间交代哪些参数、元件值怎么算、器件保证值是多少、器件怎样失效"，以及设计准则与降额数据。
ASG 画不同类型的板子时复用的是这一层，不是具体型号。

## 框架在哪里

技能运行时直接读本机的硬件设计知识框架，只读，不改：条目的补写和修订在框架里做，技能下一次运行就读到新内容。框架位置二选一指定（环境变量优先）：

1. 环境变量 `HARDWARE_KNOWLEDGE_FRAMEWORK`，值为框架目录的绝对路径；
2. 技能根目录下的本机文件 `.knowledge-framework`，一行，写框架目录的绝对路径（该文件不进版本库）。

框架目录下要有 `知识/` 和 `索引/`；否则脚本报 `KnowledgeFrameworkNotFound`，消息写明这两种办法。所有脚本只经 `scripts/knowledge_source.py` 取框架里的路径，`python3 scripts/knowledge_source.py` 打印框架目录和读取日期。
设计报告记读取日期；框架不维护版本号。

## 框架里读哪些路径

下表路径都相对框架目录。条目里的来源路径相对框架的 `原件/`；条目里指向 `设计准则/` 的链接，按准则编号查准则登记。

| 内容 | 路径 |
|---|---|
| 知识组件：需求要素、板级架构模式、接口约定、典型电路、计算方法、器件参数、器件类别、失效与故障分析（各组件回答什么见各目录的 `README.md`） | `知识/<组件>/` |
| 全部条目一览、准则编号反查条目 | `索引/条目总表.md`、`索引/准则支撑表.md` |
| 原件勘误、条目规范 | `原件勘误.md`、`条目规范.md` |
| 原件总库（数据手册、应用笔记、参考设计、标准；它指向 HardwareWiki/raw） | `原件/`；脚本经 `knowledge_source.raw_root()` 取，`find_parts.py` 和手册引用核对都从这里找 |
| 设计准则登记（G01–G09）与词表 | `知识/设计准则/准则登记/G0*_准则登记.json`、`词表.json`；`guideline_criteria.py` 读它们汇编，字段说明见 `知识/设计准则/工具/包说明/guideline-criteria.md` |
| 降额与应力规范 | `知识/设计准则/降额与应力/` 下的 `降额值.json`、`降额规范.md`、`应力判法.md`、`常规件最弱档.json` |

设计实例（范例）不属于技能读的知识组件。

电路类型和器件类别的名称、标题只在框架的 `词表.json` 里；技能的识别线索和检查按名称挂在自己的代码里。词表里有、技能还没有专门识别或检查的器件类别由 `part_classes.unhandled_kinds()` 列出。

## 设计时查什么

| 做什么 | 查 | 怎么用 |
|---|---|---|
| 读需求、提澄清 | `需求要素/端口/`、`需求要素/全板/` | 按板上的对外端口逐个查 `端口/` 的对应条目，再查 `全板/` 的条目，看需求有没有给；没给又会改变电路的按[需求澄清](requirement-clarifications.md)问 |
| 定板级方案 | `板级架构模式/`、`接口约定/` | 电源树、电压域、隔离、接地、保护分层、复位时钟等结构选择；总线和电平按总线与电平的条目 |
| 选功能块实现方案 | `典型电路/<知识域>/` | 见下文“典型电路”：逐条过“必算项”“必需外围”“已知坑” |
| 计算 | `计算方法/<知识域>/` | 按取值步骤算：每步写了输入取哪一端、算完要满足哪条准则 |
| 器件保证值 | `器件参数/` | 先查这里的保证值和页码，没有的再读手册；用 onsemi 等原件时查 `原件勘误.md` 的“文字层把‘微’抽成‘毫’的原件”一节，名单里的原件单位看页面图像，不信文字层 |
| 外部瞬态取数 | `需求要素/环境与电磁等级/` | 需求只给了标准和等级时，把等级换成波形和数值 |
| 异常工况 | `失效与故障分析/` | `器件失效方式/` 查每类器件怎样失效 |
| 任意 | `索引/准则支撑表.md`、`索引/条目总表.md` | 从准则编号反查支撑它的条目；全部条目一览 |

框架每个条目头部声明它适用的电路类型和器件类别（`电路类型：…`、`器件类别：…`）。读过的条目和每条怎样落实写在设计报告里（[quick-design.md](quick-design.md) 第 5 步）。
查到的条目与手册或标准对不上、不够用、有歧义或明显过严的，写进设计报告的“未核实与待验证”，带手册页码或本板上的实例；设计仍按框架现有内容和手册保证值走。

## 典型电路

典型电路文件在框架的 `知识/典型电路/<知识域>/<功能>.md`（文件名在各知识域之间不重复，标注和检索只用文件名），条目格式见那里的 `README.md`：头部是功能、适用范围、电路类型（设计准则库词表的电路类型名，框架的 `知识/设计准则/准则登记/词表.json`），
`## 来源清单` 给来源编号（S1、S2……，正文写 `S1 p4`），`## 选方案时比较的量` 是几种方案的比较表，`## 实现方案` 下每个 `### ` 是一个实现方案（适用范围、核心器件类、必需外围、必算项、落实规则、已知坑、来源）。
只有 `## 实现方案` 一节下的 `### ` 算实现方案；其他节里的三级标题不算。只有指路、没有实现方案的条目（如 `reviewed-bias-and-latch`）不作候选。
用 `scripts/find_parts.py --circuits <关键词>` 检索（匹配文件名、标题、功能和实现方案名）；全部条目见框架的 `索引/条目总表.md`。

任务 C6.1 写分页方案时，`page-plan.json` 每页可用 `key_blocks: [块名]` 声明关键功能块，并标注所用典型电路与实现方案：`"circuits": {"<块名>": "<典型电路文件名>#<实现方案名>"}`。
